# Хостинг и технические ограничения

## Площадка (решение владельца, сентябрь 2026)

CRM и лендинг `fortunabella.ru` размещаются на VPS **Hostkey vm.nano**:

- 2 vCPU, **2 ГБ RAM**, 60 ГБ SSD, 1 Гбит/с, 3 ТБ трафика, IPv4, около
  560 ₽/мес;
- дата-центр **в Москве** — CRM хранит персональные данные клиентов,
  граждан РФ (152-ФЗ: первичная база в России);
- виртуализация KVM (проверить при заказе: в OpenVZ/LXC Docker не
  работает);
- Ubuntu 24.04 LTS, root-доступ.

Домены: CRM — `crm.fortunabella.ru`, лендинг — `fortunabella.ru`. DNS-зона
и почтовые ящики остаются в REG.RU: меняются только A-записи на IP VPS,
MX-записи не трогаются. Поддомен бесплатный (запись в DNS-зоне).
Если почта (или DNS-зона) сейчас работает на самом хостинге Host-0, её
нужно перенести до отключения хостинга — порядок для владельца в
`docs/28-vps-owner-guide.md`.

Выбор сделан сравнением российских VPS около 500 ₽/мес с 2 ГБ RAM
(AdminVPS, Hostkey, VDSina, Aeza, Beget, Timeweb, облако REG.RU, Selectel):
Hostkey vm.nano — 2 ядра и 60 ГБ по неакционной цене в Москве.

## Как работает production

Всё запускается в Docker (`compose.prod.yaml`, подробно —
`docs/25-architecture-proposal.md`, раздел 11):

- `app` — PHP 8.4-FPM + nginx: CRM;
- `worker` — `php artisan queue:work` (уведомления, Telegram, Web Push);
- `scheduler` — `php artisan schedule:work` (напоминания по расписанию);
- `db` — MySQL 8.4 (та же версия, что в Sail), порт наружу не
  публикуется;
- `caddy` — HTTPS с автоматическим сертификатом Let's Encrypt для CRM и
  лендинга; лендинг — статический PHP-сайт со своим `send.php`.

Образ собирается в CI (GitHub Actions) и хранится в приватном реестре
GHCR; на VPS ничего не собирается.

## Бюджет памяти (2 ГБ)

Ориентир: ОС + Docker ~250 МБ, MySQL 8.4 ~350–450 МБ, PHP-FPM
~150–250 МБ, воркер и планировщик ~80 МБ, Caddy ~30 МБ, лендинг — почти
ничего. Поэтому:

- MySQL: `innodb_buffer_pool_size=256M`, `performance_schema=OFF`;
- у каждого контейнера лимит памяти; PHP-FPM — ограниченное число
  процессов;
- swap 1 ГБ;
- composer и npm на сервере не запускаются — только в CI.

## Разрешённый стек

- Backend: PHP 8.4, Laravel 13 (версия PHP задаётся образом Docker).
- База данных: MySQL 8.4.
- Frontend: Blade, Livewire, Alpine.js, Tailwind CSS; сборка — в CI
  (локально для разработки).
- Постоянные процессы: воркер очереди и планировщик Laravel в
  контейнерах.
- Очередь: database-драйвер Laravel (таблица `jobs`).
- API лендинга: REST API Laravel.
- Хранение файлов: приватный каталог `storage/app/private` в постоянном
  томе Docker, вне публичной папки.
- Push: Web Push через PHP-библиотеку (`minishlink/web-push`).
- Telegram: исходящие запросы к Telegram Bot API из PHP.

## Что не использовать в MVP

Из-за памяти 2 ГБ и простоты сопровождения:

- Redis, Celery, RabbitMQ, Kafka и другие брокеры — очередь в MySQL
  достаточна.
- WebSocket-сервер для реального времени.
- Постоянный Node.js или Python-сервер.
- Постоянный процесс Telegram-бота через long polling.
- Тяжёлую обработку документов на сервере.
- Генерацию крупных отчётов в фоне.
- Полноценный офлайн-режим CRM.
- Тяжёлую BI-аналитику.
- Хранение крупных файлов без лимитов.

## Фоновые задачи

1. Бизнес-операция записывает задание в очередь (таблица `jobs`) или
   данные для напоминания в MySQL.
2. Планировщик (`schedule:work`) по расписанию находит задачи и
   мероприятия, по которым пора напомнить, и ставит задания в очередь.
3. Воркер (`queue:work`) отправляет сообщения в Telegram Bot API и Web
   Push, повторяет неудачные попытки; окончательно упавшие задания — в
   `failed_jobs`.
4. После успешной отправки фиксируются дата и результат; повторной
   отправки без необходимости нет.
5. После деплоя воркер перезапускается (`php artisan queue:restart`).

## Push-уведомления PWA

Обязательные условия:

- CRM работает только по HTTPS (Caddy, Let's Encrypt).
- PWA устанавливается на iPhone через Safari.
- Пользователь вручную даёт разрешение на уведомления.
- На iOS push работает для установленной PWA при поддерживаемой версии iOS.
- Подписки push-уведомлений хранятся в базе данных.
- Отправка push — серверный HTTP-запрос из задания очереди.
- Если push не отправился, CRM не должна терять основную бизнес-операцию.
- Telegram остаётся резервным каналом уведомлений.

Перед внедрением проверить с VPS исходящий доступ к push-сервисам Apple и
Google и работу push на реальном iPhone (на HTTPS-стенде VPS).

## Файлы и договоры

Допустимые форматы:

- PDF: `.pdf`;
- Microsoft Word: `.doc`, `.docx`.

Требования:

- Проверять расширение файла и MIME-тип.
- Ограничить максимальный размер файла: до 10 МБ (лимиты PHP и
  веб-сервера — 12 МБ с запасом).
- Хранить случайное имя файла, а исходное имя хранить в базе.
- Не хранить загруженные документы в публичной папке сайта.
- Выдавать файл пользователю только после проверки авторизации.
- Не хранить реальные договоры в Git-репозитории.
- Документы входят в ежедневный бэкап.

## Бэкапы

- Каждую ночь на VPS: дамп БД (`mysqldump` из контейнера) + архив тома
  документов, **шифрование паролем** (это персональные данные).
- На VPS хранятся 7 последних копий.
- ПК владельца забирает копии по расписанию Windows по SSH (scp/rsync);
  если ПК выключен, копии ждут на сервере.
- Пароль шифрования хранится отдельно от архивов (не на VPS в открытом
  виде рядом с копиями, не в Git).
- Раз в месяц — проверка восстановления на чистую БД.

## Деплой

1. CI: `composer check` → сборка образа → приватный реестр GHCR.
2. На VPS: `docker compose -f compose.prod.yaml pull && up -d`.
3. `php artisan migrate --force`, кэши (`config:cache`, `route:cache`,
   `view:cache`, `event:cache`), `php artisan queue:restart`.
4. Откат — запуск предыдущего тега образа.

Секреты — только в `.env` на сервере (образец `.env.production.example`
без значений); `.env`, дампы и документы в Git не попадают.

## Подготовка сервера (один раз)

- Пользователь с SSH-ключом; вход по паролю и root по SSH запрещены.
- `ufw`: открыты только 22, 80, 443. Порты контейнеров (кроме Caddy)
  не публикуются: Docker обходит `ufw` для опубликованных портов.
- fail2ban, автоматические обновления безопасности.
- swap 1 ГБ, Docker Engine + Compose.
- Проверка исходящего доступа к `api.telegram.org`, push-сервисам Apple
  и Google.
- A-записи `crm.fortunabella.ru` и `fortunabella.ru` на IP VPS.
- Мониторинг доступности `/up` внешним пингом.

## Требования к разработке

- Локальное окружение — Sail (Docker) с теми же версиями PHP 8.4 и
  MySQL 8.4, что на VPS.
- Все тяжёлые операции выполняются экономно (память 2 ГБ).
- Все секреты хранятся только в `.env`.
- Нельзя добавлять `.env`, документы, дампы БД и папки загрузок в Git.
- Новые зависимости и сервисы проверяются на влияние на память.

## История решения

До сентября 2026 production планировался на shared-хостинге REG.RU Host-0
(ISPmanager): без Docker, без постоянных процессов, фоновые задачи только
через cron, PHP 8.4 или 8.5.7 (alt), 13 ГБ диска, лимит CPU 5,5 %. Эти
ограничения больше не действуют; следы решений под них отмечены в
`docs/25-architecture-proposal.md`.
