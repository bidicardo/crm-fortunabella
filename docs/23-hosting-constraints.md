# Хостинг и технические ограничения

## Текущая площадка

CRM планируется размещать на виртуальном хостинге REG.RU,
тариф Host-0, панель управления ISPmanager.

Это shared-хостинг: ресурсы сервера разделяются между клиентами.
Проект не должен требовать root-доступа, Docker, постоянного
запуска Node.js/Python-процессов или собственной инфраструктуры.

## Ресурсы тарифа

По информации текущего тарифа:

- Дисковое пространство: 13 ГБ.
- Сайты и поддомены: до 7.
- MySQL-базы: без ограничения по количеству.
- Среднесуточная нагрузка CPU: до 5,5%.
- Поддержка SSL: есть.
- Доступ по SSH: есть.
- Доступ по FTP/SFTP: есть.
- phpMyAdmin: есть.
- Cron-задачи: есть.
- Почтовые ящики и переадресация: есть.
- Антивирус и антиспам: есть.

## Версия PHP

На хостинге REG.RU доступна PHP 8.5.7 (alt).

PHP 8.5.7 может использоваться для production после проверки
совместимости всех Composer-зависимостей проекта.

Предпочтительная версия production:

- PHP 8.4, если она доступна в панели ISPmanager;
- PHP 8.5.7 (alt), если PHP 8.4 недоступна либо все зависимости
  успешно установлены и прошли тестирование на PHP 8.5.7.

Локальная среда разработки должна использовать ту же основную
версию PHP, что будет выбрана на production.

## Разрешённый стек MVP

- Backend: PHP 8.4 или PHP 8.5.7 (alt).
- Framework: Laravel 13.
- База данных: MySQL или MariaDB.
- Frontend: Laravel Blade, HTML, CSS и JavaScript.
- Стили: Tailwind CSS.
- Сборка frontend: локально на компьютере разработчика.
- API лендинга: REST API Laravel.
- Планировщик задач: Laravel Scheduler через cron.
- Хранение файлов: защищённый каталог вне публичной папки сайта.
- Push: Web Push через PHP-библиотеку, совместимую с выбранной версией PHP.
- Telegram: исходящие запросы к Telegram Bot API из PHP.

## Что не использовать в MVP

Не закладывать в обязательную первую версию:

- Docker на production-хостинге.
- Постоянный Node.js-сервер.
- Постоянный Python-сервер FastAPI/Django.
- Постоянный процесс Telegram-бота через long polling.
- Redis как обязательную зависимость.
- Celery, RabbitMQ, Kafka и другие брокеры очередей.
- WebSocket-сервер для реального времени.
- Тяжёлую обработку документов на сервере.
- Генерацию крупных отчётов в фоне.
- Полноценный офлайн-режим CRM.
- Тяжёлую BI-аналитику.
- Хранение крупных файлов без лимитов.

## Ограничения фоновых задач

На shared-хостинге нет гарантии, что будет работать постоянный worker.
Поэтому фоновые задачи должны быть реализованы через cron и базу данных.

Подход для MVP:

1. Система записывает уведомления и запланированные действия в MySQL.
2. Cron регулярно запускает команду планировщика Laravel.
3. Планировщик находит задачи и мероприятия, для которых пора отправить уведомление.
4. PHP отправляет сообщение в Telegram Bot API.
5. После успешной отправки фиксируется дата и результат.
6. Повторная отправка не должна происходить без необходимости.

Нельзя зависеть от постоянно работающей очереди Laravel Worker.

## Push-уведомления PWA

Push-уведомления требуют отдельной проверки перед реализацией.

Обязательные условия:

- CRM работает только по HTTPS.
- PWA устанавливается на iPhone через Safari.
- Пользователь вручную даёт разрешение на уведомления.
- На iOS push работает для установленной PWA при поддерживаемой версии iOS.
- Подписки push-уведомлений хранятся в базе данных.
- Отправка push должна быть реализована через серверный HTTP-запрос.
- Если push не отправился, CRM не должна терять основную бизнес-операцию.
- Telegram остаётся резервным каналом уведомлений.

Перед внедрением нужно проверить:
- доступность PHP-библиотеки для Web Push;
- наличие Composer;
- возможность выполнения исходящих HTTPS-запросов;
- лимиты cron;
- работу push на реальном iPhone.

## Файлы и договоры

Допустимые форматы:

- PDF: `.pdf`;
- Microsoft Word: `.doc`, `.docx`.

Требования:

- Проверять расширение файла и MIME-тип.
- Ограничить максимальный размер файла.
- Рекомендуемый лимит MVP: до 10 МБ на файл.
- Хранить случайное имя файла, а исходное имя хранить в базе.
- Не хранить загруженные документы в публичной папке сайта.
- Выдавать файл пользователю только после проверки авторизации.
- Не хранить реальные договоры в Git-репозитории.
- Делать резервную копию базы и каталога документов.

## Деплой

Разработка выполняется локально.

На хостинг отправляются:

- PHP-код;
- готовые frontend-assets;
- Composer-зависимости, если Composer доступен по SSH;
- миграции базы данных;
- настройки окружения через `.env`, который не попадает в Git.

Перед первым деплоем необходимо проверить:

- точную версию PHP;
- доступность Composer;
- доступность SSH;
- путь к PHP в cron;
- доступные расширения PHP;
- лимит памяти PHP;
- максимальный размер upload-файла;
- лимит времени выполнения скрипта;
- возможность исходящих HTTPS-запросов;
- поддерживаемую версию MySQL/MariaDB.

## Требования к разработке

- Проект должен работать без Docker в production.
- Проект должен запускаться на обычном PHP-хостинге.
- Все тяжёлые операции должны выполняться экономно.
- Нельзя использовать обязательные сервисы, требующие root-доступа.
- Нельзя требовать постоянно работающий серверный процесс.
- Все секреты должны храниться только в `.env`.
- Нельзя добавлять `.env`, документы, дампы БД и папки загрузок в Git.
- При выборе библиотек необходимо проверять совместимость с PHP-версией хостинга.
- До создания архитектуры необходимо уточнить реальные версии PHP и MySQL/MariaDB в ISPmanager.

## Проверка совместимости перед разработкой

Перед созданием production-версии необходимо:

1. Выбрать версию PHP в ISPmanager.
2. Проверить версию PHP в SSH:
   `php -v`.
3. Проверить Composer:
   `composer --version`.
4. Проверить расширения PHP:
   `php -m`.
5. Создать чистый Laravel-проект.
6. Выполнить `composer install`.
7. Установить предполагаемые ключевые зависимости:
   - Web Push;
   - Telegram;
   - экспорт Excel;
   - работа с телефонами;
   - тестирование.
8. Запустить тесты.
9. Зафиксировать выбранную версию PHP в документации.
