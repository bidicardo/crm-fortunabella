# Архитектурное предложение

Документ описывает предлагаемую техническую архитектуру Fortuna CRM на
основе требований (`docs/01`–`docs/22`), ограничений хостинга
(`docs/23-hosting-constraints.md`) и реального примера интеграции с
лендингом (`docs/24-exaple-sendphp-from-site.md`, уже отражён в
`docs/13-landing-api.md`).

Решения этого документа приняты и реализуются: стек установлен, выполнены
Фазы 0, 1, 1а, задачи 13–19 Фазы 2, дизайн-система Д1, страница входа Д2 и карточка клиента 19а (см. раздел
«Статус выполнения» в конце). Если реализация отличается от первоначального предложения, ниже
это отмечено явно (например, вход сделан без Laravel Breeze).

**Площадка (решение владельца, сентябрь 2026):** CRM и лендинг переезжают
с shared-хостинга REG.RU Host-0 на VPS Hostkey vm.nano (Москва, 2 ГБ RAM) и
работают в Docker-контейнерах (`docs/23-hosting-constraints.md`). Разделы
ниже обновлены под это; где решение изначально объяснялось ограничениями
shared-хостинга, это отмечено.

Общий принцип выбора: не закладывать инфраструктуру сложнее, чем
вмещает небольшой VPS (2 ГБ RAM, `docs/23`), и такую, которую сможет
самостоятельно поддерживать один начинающий разработчик, опираясь на
Claude Code — то есть минимум "движущихся частей", максимум
стандартных, хорошо задокументированных решений.

---

## 1. Backend-стек

**Решение**: PHP 8.4 (предпочтительно) или PHP 8.5.7 (alt), фреймворк
**Laravel 13**.

**Зачем.** Версия PHP и Laravel уже зафиксированы в `docs/23` как
требование хостинга. Laravel даёт "из коробки" почти всё, что нужно
CRM: аутентификацию, валидацию, миграции БД, очереди на базе БД,
планировщик задач, файловое хранилище, ORM. Это резко сокращает объём
кода, который придётся писать и поддерживать вручную.

**Плюсы**
- Огромное сообщество и документация — Claude Code хорошо знает
  Laravel-паттерны, меньше риск "придуманных" решений.
- Все нужные для MVP подсистемы уже встроены, не нужно собирать стек
  из отдельных библиотек.
- Простая модель развёртывания на обычном PHP-хостинге (без отдельного
  рантайма/процесса).

**Минусы**
- Монолитная архитектура — при сильном росте потребует более
  вдумчивого разделения на модули (для MVP это не проблема).
- Версия PHP (8.4) и расширения задаются образом Docker — одинаково
  локально (Sail) и на VPS; отдельная проверка совместимости с хостингом
  больше не нужна.

## 2. Frontend-стек

**Решение**: TALL-стек — **T**ailwind CSS + **A**lpine.js + **L**aravel
+ **L**ivewire. Без отдельного SPA-фреймворка (React/Vue) и без
отдельного JSON API для интерфейса.

**Зачем.** Laravel рендерит HTML-страницы (Blade), Livewire добавляет
интерактивность (обновление частей страницы без полной перезагрузки)
прямо на PHP, без необходимости писать и синхронизировать отдельный
JS-стейт и отдельный REST/JSON API только ради интерфейса. Для
drag-and-drop канбана — встроенный в Livewire 4 `wire:sort` (плагин
Alpine x-sort, уже в сборке Livewire; отдельный пакет SortableJS не
нужен); для календаря — готовый JS-виджет FullCalendar.

**Плюсы**
- Один язык бэкенда и фронтенда (PHP + немного JS) — проще
  поддерживать одному разработчику.
- Нет дублирования бизнес-логики (валидация, права доступа) между
  backend и отдельным frontend-приложением.
- Меньше собираемых артефактов и зависимостей (нет отдельного
  npm-приложения с собственным роутингом, стейт-менеджером и т. д.).

**Минусы**
- Меньше гибкости для очень сложных, "нативных" по ощущениям
  интерфейсов — для CRM среднего размера это не критично.
- Канбан и календарь всё равно требуют аккуратной работы с JS-виджетами
  поверх Livewire (не "бесплатно").

## 3. База данных

**Решение**: **MySQL 8.4** — одна и та же версия в Sail и в
production-контейнере на VPS; кодировка `utf8mb4`, движок InnoDB. На VPS
настроена под 2 ГБ RAM: `innodb_buffer_pool_size=256M`,
`performance_schema=OFF`, лимит памяти контейнера; порт наружу не
публикуется.

**Зачем.** Изначально — требование shared-хостинга REG.RU; после переезда
на VPS оставлена та же СУБД (решение владельца), чтобы окружения
разработки и production совпадали.

**Плюсы**
- Одинаковая СУБД локально и на VPS — никаких расхождений поведения.
- InnoDB даёт транзакции и внешние ключи — важно для целостности связей
  Client/Deal/Counterparty.

**Минусы**
- MySQL/MariaDB менее строг по умолчанию, чем PostgreSQL (например, в
  обработке дат/пустых строк) — нужно явно включать строгий режим
  (`strict mode`) в конфигурации Laravel.

## 4. ORM и миграции

**Решение**: Eloquent ORM (встроен в Laravel) + стандартные
Laravel-миграции.

**Зачем.** Eloquent не требует установки — он уже часть Laravel.
Миграции дают читаемую, версионируемую историю изменений схемы прямо в
Git — удобно смотреть, что именно поменялось, и удобно поэтапно
наращивать модель данных вместе с Claude Code, задача за задачей.

**Плюсы**
- Ноль дополнительных зависимостей.
- Миграции = самодокументирующаяся история схемы, легко откатить.
- Много готовых паттернов (factories, seeders) для тестовых данных.

**Минусы**
- ORM может маскировать N+1-запросы, если не использовать eager
  loading (`with()`) — стоит с самого начала внести это как соглашение
  в код-ревью/тесты.

## 5. Авторизация

**Решение**: встроенная сессионная аутентификация Laravel — без открытой
регистрации. Laravel Breeze **не используется**: вход, выход, приглашения и
блокировка сделаны собственными Livewire-компонентами (меньше лишнего кода
и маршрутов, например регистрации и сброса пароля). Отдельно
— собственная модель `Invite` с одноразовым токеном для регистрации
сотрудников. Для эндпоинта лендинга — отдельная простая проверка
секретного токена в заголовке запроса (middleware), без OAuth/Sanctum.

**Зачем.** CRM — не публичный сервис с множеством внешних API-клиентов,
а внутренний инструмент с одним доверенным внешним клиентом (лендинг).
Сессионная авторизация — самый простой и наименее подверженный ошибкам
вариант для веб-интерфейса; токен в заголовке — самый простой
достаточный вариант для одного доверенного клиента.

**Плюсы**
- Минимум кода и зависимостей, всё встроено в Laravel.
- Модель Invite прямо соответствует описанному в `docs/03` флоу
  (одноразовый токен, самостоятельная установка пароля).

**Минусы**
- Секретный токен лендинга нужно вручную ротировать при компрометации
  (нет автоматического refresh, как в OAuth) — для одного клиента это
  приемлемо.

## 6. Хранение документов

**Решение**: Laravel Filesystem с приватным диском вне `public/`.
Скачивание — только через авторизованный контроллер, который проверяет
права и стримит файл.

**Зачем.** Документы (договоры) не должны быть доступны по прямой
ссылке без авторизации (`docs/19`, `docs/23`). Локальный приватный диск
не требует внешнего облачного хранилища; на VPS каталог
`storage/app/private` лежит в постоянном томе Docker.

**Плюсы**
- Не нужен S3 или другой облачный сервис для MVP — меньше внешних
  зависимостей и затрат.
- Абстракция дисков Laravel позволяет в будущем переключиться на
  S3-совместимое хранилище, поменяв только конфигурацию, а не код.

**Минусы**
- Файлы хранятся на одном сервере — точка отказа. Нужен ежедневный
  зашифрованный бэкап тома документов вместе с дампом БД с копией на ПК
  владельца (`docs/19`, `docs/23`).

## 7. Очередь задач и планировщик уведомлений

**Решение**: database-драйвер очереди Laravel (`QUEUE_CONNECTION=database`,
задачи в таблице `jobs`) + **постоянный воркер** `php artisan queue:work`
и **планировщик** `php artisan schedule:work` — отдельные контейнеры из
того же образа, что и приложение, с автоперезапуском (`restart: always`).

**Зачем.** На VPS постоянные процессы разрешены (`docs/23`). Воркер
отправляет уведомления сразу, повторяет неудачные попытки и складывает
окончательно упавшие задачи в `failed_jobs`. Планировщик по расписанию
находит, что нужно отправить (просроченные задачи, напоминания о
мероприятиях), и ставит это в очередь. Redis и брокеры не нужны — очередь
в MySQL уже есть и укладывается в 2 ГБ.

(До переезда решение было «cron раз в минуту + `queue:work
--stop-when-empty`» — единственный вариант на shared-хостинге.)

**Плюсы**
- Нет задержки cron; штатные повторы и журнал ошибок Laravel.
- Нет дополнительной инфраструктуры (брокеров сообщений).

**Минусы**
- Два дополнительных процесса (~80 МБ RAM) — учтено в бюджете памяти VPS.
- Воркер держит код в памяти: после деплоя его нужно перезапускать
  (`php artisan queue:restart` в скрипте деплоя).

## 8. Способ реализации PWA

**Решение**: стандартный `manifest.json` + простой service worker,
кэширующий статику (иконки, app shell), без сложной офлайн-логики.

**Зачем.** `docs/16` явно требует установку на iPhone через Safari и
работу как приложения с домашнего экрана, но при этом "достаточно
работы при наличии интернета" — то есть не нужен полноценный офлайн-режим,
а значит service worker можно сделать простым, без сложной синхронизации
данных.

**Плюсы**
- Минимальный service worker — меньше кода, меньше багов с
  устаревшим кэшем.
- Не требует отдельного фреймворка для PWA — Laravel просто отдаёт эти
  файлы как статику.

**Минусы**
- Если в будущем понадобится офлайн-режим — потребуется отдельная
  доработка (сознательно отложено, см. `docs/02-mvp-scope.md`).

## 9. Способ push-уведомлений для iPhone

**Решение**: Web Push (VAPID) через PHP-библиотеку `minishlink/web-push`
(указана как рекомендованная в `docs/23`). Подписки хранятся в таблице
`push_subscriptions`, отправка — заданиями очереди через тот же воркер,
что и остальные уведомления (см. п. 7).

**Зачем.** Это стандартный способ слать push в PWA на iPhone — обычный
HTTP-запрос к push-сервису Apple/браузера из PHP.

**Плюсы**
- Не требует стороннего сервиса рассылки (Firebase и т.п.).
- Обычный исходящий HTTPS-запрос; доступ с VPS к push-сервисам Apple и
  Google проверяется при подготовке сервера.

**Минусы**
- iOS поддерживает push только для PWA, установленной на домашний
  экран, начиная с определённой версии iOS, и только после явного
  разрешения пользователя (`docs/16`) — это ограничение платформы, не
  реализации.
- Если push не пришёл (пользователь не разрешил/отключил), CRM должна
  продолжать работать — Telegram остаётся резервным каналом.

## 10. Способ интеграции с Telegram

**Решение**: переиспользовать паттерн из `docs/24-exaple-sendphp-from-site.md`
— исходящие HTTP-запросы к Telegram Bot API (`sendMessage`) через cURL
из PHP, обёрнутые в отдельный сервис/канал уведомлений Laravel.
Отправка — заданиями очереди через воркер (п. 7), без long polling и без
постоянного процесса бота.

**Зачем.** Уже есть рабочий, проверенный код именно этого подхода
(текущий скрипт на лендинге). CRM нужно только отправлять сообщения
(не принимать команды от пользователей в боте), поэтому webhook/long
polling не требуются вовсе.

**Плюсы**
- Код уже существует и проверен в проде (лендинг), логику можно
  напрямую перенести в сервис уведомлений CRM. Доступ с VPS к
  `api.telegram.org` проверяется при подготовке сервера.
- Минимум инфраструктуры — обычный исходящий HTTP-запрос.

**Минусы**
- Если понадобится двусторонний бот (принимать команды) — потребуется
  либо webhook (публичный HTTPS-эндпоинт на VPS есть), либо polling (для которого действительно нужен
  постоянный процесс) — это не входит в MVP.

## 11. Docker: разработка (Sail) и production (VPS)

**Решение.**
- **Разработка** — Laravel Sail (PHP 8.4 + MySQL 8.4 + Mailpit),
  `compose.yaml` в корне проекта.
- **Production** — отдельная конфигурация `compose.prod.yaml` на VPS
  Hostkey vm.nano (Москва, 2 ГБ RAM, Ubuntu 24.04):
  - `app` — PHP 8.4-FPM + nginx, образ собирается в CI (код, зависимости
    Composer без dev и готовые `public/build` внутри образа);
  - `worker` (`queue:work`) и `scheduler` (`schedule:work`) — тот же образ;
  - `db` — MySQL 8.4 с настройками под 2 ГБ, том `db-data`, порт наружу не
    публикуется;
  - `caddy` — HTTPS-прокси с автоматическим сертификатом Let's Encrypt для
    `crm.fortunabella.ru` и лендинга `fortunabella.ru` (лендинг —
    статический PHP-сайт на том же сервере).
- **Сборка и деплой** — GitHub Actions: `composer check` → multi-stage
  образ (composer `--no-dev`, `npm run build`, в итоговом образе нет
  Node) → приватный реестр GHCR → на VPS `docker compose pull && up -d`,
  затем `php artisan migrate --force`, кэши конфигурации/маршрутов/видов
  и `queue:restart`. На VPS ничего не собирается (не хватит памяти).
- **Бэкапы** — ночной скрипт на VPS: `mysqldump` + архив тома документов,
  шифрование паролем, 7 последних копий на сервере; ПК владельца забирает
  их по расписанию по SSH.

**Зачем.** Одинаковые контейнеры локально и на сервере убирают класс
ошибок «локально работает, на хостинге нет»; постоянные процессы (воркер,
планировщик) и HTTPS с автопродлением — штатные.

**Плюсы**
- Одна версия PHP/MySQL и одни расширения везде.
- Деплой — одна команда, откат — предыдущий тег образа.

**Минусы**
- Администрирование сервера (обновления ОС, файрвол, SSH-ключи,
  fail2ban, бэкапы, мониторинг `/up`) — на владельце, по чек-листу
  `docs/23` и `docs/19`.
- Память ограничена 2 ГБ: без Redis и тяжёлых сервисов, лимиты памяти
  контейнеров, swap 1 ГБ.

(До сентября 2026 production планировался на shared-хостинге REG.RU без
Docker; Sail был только для разработки.)

## 12. Структура папок проекта

Стандартная структура Laravel-приложения, доменная логика CRM
раскладывается так:

```
app/
  Models/            Eloquent-модели: User, Invite, Client, Counterparty,
                      CounterpartyContact, Deal, Task, Document,
                      LeadSubmission, ActivityLog, Notification,
                      PushSubscription
  Models/Concerns/    Трейты моделей (LogsActivity — история изменений)
  Enums/              Перечисления (Role, ClientLegalType)
  Rules/              Правила валидации (RussianPhone)
  Support/            Вспомогательные классы (Navigation — меню и стрелка «Назад»)
  Livewire/           Компоненты экранов. Готовы: Home, Login, AcceptInvite,
                      Users, ClientTable, ClientForm, ClientShow, ClientMerge.
                      Планируются: DealsKanban, CounterpartiesKanban,
                      DealCard, Dashboard, Calendar
  Services/           Доменные сервисы без UI. Готовы: PhoneNormalizer,
                      DuplicateFinder, ClientMergeService.
                      Планируются: LeadImportService, TelegramNotifier,
                      WebPushSender
  Notifications/      Классы уведомлений Laravel (email/telegram/push-каналы)
  Http/
    Controllers/      Тонкие контроллеры (в основном не-Livewire маршруты:
                      API лендинга, скачивание документов, auth)
    Middleware/        Проверка токена лендинга, roles/permissions
config/
  navigation.php      Единый источник левого меню, нижней панели и правила
                      «Назад» (только массивы, без замыканий)
  crm.php             Настройки CRM (срок приглашения и т. п.)
database/
  migrations/         История схемы БД
  factories/          Фейковые данные для тестов (без реальных клиентов)
  seeders/
resources/
  views/              Blade-шаблоны и Livewire-вьюхи
routes/
  web.php             Веб-интерфейс (сессионная авторизация)
  api.php             Эндпоинт приёма заявок с лендинга
tests/
  Feature/            Тесты по сценариям (HTTP, Livewire-компоненты)
  Unit/               Тесты чистой логики (нормализация телефона и т.д.)
```

**Зачем такая структура.** Она стандартна для Laravel — при появлении
новой функциональности Claude Code (и человек-разработчик) сразу знает,
куда класть новый код, не изобретая свою организацию проекта.

## 13. Стратегия тестирования

**Решение**: Pest (или PHPUnit — оба штатно доступны в Laravel).
Feature-тесты — на уровне HTTP/Livewire-сценариев (приглашение и вход,
приём заявки с лендинга, переходы по канбану, слияние дублей клиентов,
загрузка/скачивание документов). Unit-тесты — на чистую логику
(нормализация телефона, поиск дублей). Тестовая БД — SQLite in-memory
для скорости, если код не полагается на MySQL-специфичные функции.
Никаких реальных клиентских данных в тестах — только фабрики/фейкер
(по правилу `CLAUDE.md`).

**Зачем.** Каждая задача из списка ниже должна оставлять после себя
минимум один проверяемый тест — это прямо соответствует правилу
"ponytail" в `CLAUDE.md`/системных инструкциях (нетривиальная логика не
считается законченной без теста) и защищает от регрессий при
дальнейшей пошаговой разработке через Claude Code.

**Плюсы**
- Встроено в Laravel, не требует дополнительной настройки CI с нуля.
- Feature-тесты по сценариям — надёжная защита при поэтапной разработке
  большими шагами через Claude Code.

**Минусы**
- SQLite в тестах может скрыть расхождения с реальным MySQL в редких
  случаях (например, коллации, специфичные функции даты) — при
  подозрении на такие расхождения тест стоит прогонять и на MySQL.

## План задач для Claude Code

Каждая задача — самостоятельный, проверяемый шаг размером примерно в
одну сессию. Задачи идут по возрастанию, от фундамента к полной CRM;
каждая следующая опирается на предыдущие. После задач с моделями/логикой
всегда идёт задача с тестами на неё же — не откладывать тесты на потом.

### Фаза 0 — Bootstrap
1. Создать проект Laravel 13, настроить `.env.example`, базовый README
   для разработчика (как поднять окружение).
2. Настроить Laravel Sail для локальной разработки (PHP + MySQL +
   Mailpit), проверить `sail up`.
3. Подключить TALL-стек: Tailwind CSS, Alpine.js, Livewire; настроить
   сборку через Vite.
4. Настроить Laravel Pint (форматирование) и Pest как тестовый фреймворк.
5. Добавить базовый скрипт/CI-шаг «прогнать тесты и линтер одной командой».

6. Миграция и модель `User` (роль: creator/member, статус блокировки).

### Фаза 2а — Прод-окружение на VPS (по команде владельца (срок не назначен))
Решение владельца: CRM и лендинг — на VPS Hostkey vm.nano (Москва, 2 ГБ),
в Docker (`docs/23`, раздел 11 выше). Запускается по команде владельца;
после неё
дальше каждая фаза проверялась на настоящем HTTPS (iPhone, PWA, push,
копирование в буфер). Промпт — `docs/prompts/04-vps-production.md`.
20.1. Подготовка VPS: Ubuntu 24.04, пользователь с SSH-ключом (вход по
    паролю и root по SSH запрещены), ufw (22/80/443), fail2ban,
    автоматические обновления безопасности, swap 1 ГБ, Docker Engine +
    Compose; проверка доступа с сервера к `api.telegram.org` и к
    push-сервисам Apple/Google. Инструкция + скрипт в репозитории.
20.2. Production-образ и `compose.prod.yaml`: multi-stage Dockerfile
    (PHP 8.4-FPM + nginx, composer `--no-dev`, `npm run build`),
    контейнеры app/worker/scheduler/db (MySQL 8.4 под 2 ГБ)/caddy (HTTPS
    для `crm.fortunabella.ru` и `fortunabella.ru`), лимиты памяти, тома
    `storage` и `db-data`, доверенные прокси в Laravel, prod-`.env` по
    образцу `.env.production.example`. Проверка: локальный запуск,
    `/up` = 200.
20.3. CI и деплой: GitHub Actions (`composer check` → образ → GHCR),
    скрипт деплоя на VPS (pull, up, migrate, кэши, `queue:restart`),
    откат на предыдущий тег. Перенос лендинга на VPS, A-записи в DNS
    REG.RU.
20.4. Бэкапы: ночной зашифрованный архив (дамп БД + документы), 7 копий
    на VPS, забор на ПК владельца по расписанию Windows, проверка
    восстановления на чистую БД.
