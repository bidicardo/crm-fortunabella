## Принятые решения (повторно не обсуждать)

- Обязательное поле клиента — только имя (или название организации).
  Телефон, email и остальное необязательны.
- Тип клиента — два поля: юридический тип (`individual` — физическое
  лицо, `organization` — организация) и роль — свободный текст без
  заданных вариантов (например, «невеста», «организатор»). Оба поля
  необязательны.
- Телефоны только российские: после удаления всех нецифровых символов
  ровно 11 цифр, первая 7 или 8 (8 заменяется на 7); хранится как
  `+7XXXXXXXXXX`. Всё остальное отклоняется.
- Дубли не запрещаются: система предупреждает и даёт выбор «открыть
  существующего» или «продолжить создание». Уникальных индексов по
  телефону и email в БД нет.
- Слияние дублей доступно любому пользователю CRM (создателю и
  участникам). Дубль не удаляется, а архивируется.
- Клиентов нельзя удалять (кроме архивации при слиянии).
- Права: все страницы клиентов доступны любому авторизованному
  пользователю (создатель и участник равны).

## Общие правила для всех задач Фазы 2

- Интерфейс на русском; Blade + Livewire 4 + Tailwind; страницы в
  layout `resources/views/layouts/app.blade.php`; маршруты через
  `Route::livewire(...)` в группе `auth` файла `routes/web.php`
  (как уже сделано для `/users`).
- Маршруты страниц клиентов именованные: `clients.index` (список),
  `clients.create`, `clients.show`, `clients.edit`. Левое меню находит
  пункт «Клиенты» по имени `clients.index` (`config/navigation.php`,
  Фаза 1а). У каждой страницы задаётся #[Title('...')] — это название
  раздела в верхней панели. Стрелка «Назад» в верхней панели ведёт в
  родительский раздел автоматически (`Navigation::backUrl()`, правило в

- Новые миграции — отдельными файлами, существующие не менять;
  должны работать и на MySQL (Sail), и на SQLite (тесты).
- Тесты — Pest, SQLite in-memory, только фабрики и выдуманные данные.
  Для нетривиальной логики тест пишется в той же задаче.
- Не устанавливать новые пакеты без подтверждения.
- Запуск проверок: `composer check`; в Sail на Windows:
  `docker compose exec laravel.test composer check`.
- Ничего не коммитить; в конце показать `git status` и `git diff`.

## Задача 14 — Нормализация телефона

```
Прочитай CLAUDE.md, docs/08-clients.md (раздел «Телефон»),
docs/13-landing-api.md (раздел «Нормализация телефона») и
docs/25-architecture-proposal.md (задача 14 Фазы 2). Задача 13
выполнена (модель Client).

Сделай сервис нормализации телефона. Он будет использоваться формой
клиента, поиском, поиском дублей и приёмом заявок с лендинга (Фаза 5),
поэтому логика должна быть в одном месте.

Что нужно сделать:
1. Класс App\Services\PhoneNormalizer без зависимости от БД и
   фреймворка, метод normalize(?string $raw): ?string:
   - пустое значение или строка без цифр → null;
   - удалить все нецифровые символы; если получилось ровно 11 цифр и
     первая 7 или 8 — вернуть '+7' + последние 10 цифр;
   - всё остальное (иное количество цифр, другая первая цифра,
     иностранные номера) → null.
   Метод isValid(?string $raw): bool — true, если normalize() вернул
   значение.
2. Правило валидации App\Rules\RussianPhone (для форм), использующее
   этот же сервис, с русским сообщением об ошибке, например
   «Введите российский номер: 11 цифр, например +7 917 123-45-67».
   Пустое значение правило пропускает (поле необязательное).
3. Модель Client: при записи phone через форму сохраняется уже
   нормализованное значение (например, через мутатор/cast на
   PhoneNormalizer); строка, которую нельзя нормализовать, в БД
   попасть не должна. Явно решить и описать в коде одной строкой,
   что происходит при попытке присвоить невалидное значение
   напрямую (рекомендуется: сохраняется null; отклонение — на
   уровне формы правилом RussianPhone).
4. Unit-тесты (Pest dataset) обязательно с примерами из документов:
   `89171234567`, `8 917 123-45-67`, `+7 917 123-45-67`,
   `7 (917) 123-45-67` → `+79171234567`; отрицательные случаи:
   10 цифр, 12 цифр, первая цифра 9, `+380 44 123 45 67`, буквы,
   пустая строка, null → null. Feature-тест: правило RussianPhone и
   сохранение клиента с телефоном `8 917 123-45-67` даёт в БД
   `+79171234567`.

Не создавать экраны и не менять скрипт лендинга — он вне репозитория.

В конце запусти composer check и покажи git status и git diff,
ничего не коммить.
```

## Задача 18 — Слияние дублей

```
Прочитай CLAUDE.md, docs/18-deduplication.md, docs/08-clients.md
(раздел «Слияние дублей»), docs/05-business-rules.md (раздел
«Клиенты») и docs/25-architecture-proposal.md (задача 18 Фазы 2).

(они появятся в Фазах 4, 6, 7) — слияние должно быть спроектировано
так, чтобы к ним легко добавить перенос.

Что нужно сделать:
1. Новая миграция для clients: merged_into_id (nullable FK на
   clients), merged_by (nullable FK на users), merged_at (nullable

   Client $duplicate, array $fieldChoices, User $by): void — всё в
   одной транзакции:
   - нельзя сливать клиента с самим собой, архивного клиента или
     клиента, уже влитого в другого — понятная ошибка;
   - основной клиент получает значения полей по выбору пользователя
     ($fieldChoices: для каждого поля 'main' или 'duplicate'; по
     умолчанию берётся значение основного, а если оно пустое — из
     дубля; примечания по умолчанию объединяются через пустую строку);
```
