# Интеграция с лендингом

## Источник

Лендинг:
https://fortunabella.ru

## Текущая реализация

На лендинге уже работает пример PHP-скрипта приёма формы
(`docs/24-exaple-sendphp-from-site.md`). Сейчас он отправляет заявку
напрямую в Telegram, минуя CRM. Скрипт будет переписан так, чтобы
отправлять заявку в CRM API — набор полей, правила валидации,
ограничение частоты запросов и формат ответа ниже зафиксированы по
этому скрипту, чтобы новый CRM-эндпоинт был с ним совместим.

## Форма

Поля, которые реально отправляет лендинг:
- name — имя (до 80 символов);
- phone — телефон (до 40 символов);
- email — email (до 120 символов, необязательно);
- social — социальная сеть или мессенджер (до 120 символов, необязательно);
- details — описание запроса (до 1500 символов, необязательно);
- consent — согласие на обработку персональных данных (чекбокс, обязателен);
- company — скрытое honeypot-поле для защиты от ботов; не является
  данными клиента и не должно попадать в карточку клиента/заявки.

Обязательные поля (по фактической валидации):
- имя — минимум 2 символа;
- телефон — после нормализации должен содержать ровно 11 цифр;
- согласие на обработку персональных данных.

Email, если указан, должен проходить проверку формата. Описание запроса
необязательно — CRM должна принимать заявку и без него.

## Формат запроса

- Метод: только POST; остальные методы отклоняются (405).
- Тело: JSON (`application/json`) либо обычная форма
  (`application/x-www-form-urlencoded`) — CRM должна принимать оба варианта.
- Ограничение размера тела запроса (в примере — 20 000 байт).

## Формат ответа

JSON-объект `{"ok": true|false, "error"?: string}`.

Коды ответа:
- 200 — заявка принята (в том числе если она тихо отклонена как спам
  через honeypot — тоже отвечаем `{"ok": true}`, чтобы не выдавать
  наличие защиты);
- 405 — неверный метод запроса;
- 422 — ошибка валидации полей;
- 429 — превышен лимит частоты запросов;
- 500 — ошибка конфигурации сервера;
- 502 — заявку не удалось доставить дальше (например, в Telegram или в CRM).

## Защита от ботов

Honeypot-поле `company`: скрыто от реальных пользователей стилями,
боты его заполняют. Если поле непустое — заявка не обрабатывается, но
сервер всё равно отвечает `{"ok": true}`.

## Ограничение частоты запросов

Не более одного запроса с одного IP за настраиваемый интервал (в
примере по умолчанию 60 секунд). При превышении — ответ 429.

Пример использует временный файл, привязанный к хешу IP — это
достаточно для одиночного PHP-хостинга без постоянных процессов
(см. `docs/23-hosting-constraints.md`), но не переживает несколько
серверов/деплоев. Для CRM API стоит хранить это состояние в БД
(MySQL/MariaDB), а не во временных файлах.

## Сценарий заявки (целевой, после переноса на CRM API)

1. Пользователь заполняет форму на сайте.
2. Лендинг отправляет POST-запрос в CRM (JSON или form-data, поля — см. выше).
3. CRM проверяет секретный токен.
4. CRM проверяет honeypot-поле и лимит частоты запросов.
5. CRM проверяет обязательные поля (имя, телефон, согласие).
6. CRM нормализует номер телефона.
7. CRM ищет клиента по телефону.
8. Если клиент найден, создаётся новая сделка и связывается с ним.
9. Если клиент не найден, создаются клиент и сделка.
10. Сделка получает статус «Новая заявка».
11. Исходная заявка (включая факт согласия на обработку данных)
    сохраняется в журнале LeadSubmission.
12. Пользователи получают уведомление.
13. Уведомление дублируется в Telegram — текущий скрипт уже умеет
    отправлять форматированное сообщение через Telegram Bot API, этот
    код переиспользуется для дублирования уведомлений CRM.

## Дубликаты

Если телефон найден:
- не создавать нового клиента;
- создать новую сделку;
- связать сделку с существующим клиентом.

## Безопасность

- Секретный токен для эндпоинта CRM.
- Honeypot-поле от ботов.
- Ограничение частоты запросов (см. выше).
- Проверка формата входящих данных.
- Журнал успешных и ошибочных запросов.
- Защита от повторной обработки одного запроса.

## Нормализация телефона

Правило, подтверждённое реальной валидацией в скрипте лендинга: из
номера удаляются все нецифровые символы, результат должен содержать
ровно 11 цифр (российский номер вида `7XXXXXXXXXX` или `8XXXXXXXXXX`).
Номера, не сводящиеся к 11 цифрам, считаются невалидными и отклоняются
при приёме заявки (ответ 422), а не сохраняются «как есть».

Для хранения в CRM номер приводится к формату E.164 (`+7XXXXXXXXXX`),
ведущая `8` заменяется на `7`.

Примеры одного и того же номера:
- `89171234567`;
- `8 917 123-45-67`;
- `+7 917 123-45-67`;

→ хранится как `+79171234567`.
